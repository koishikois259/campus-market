# 状态图与时序图初稿说明

日期：2026-11-03；版本：状态图简洁初稿 v0.2，时序图 AI 初稿 v0.1。

两图沿用实验一需求与现有类图、组件图。符号参考 [PlantUML 状态图](https://plantuml.com/zh/state-diagram) 和 [PlantUML 时序图](https://plantuml.com/zh/sequence-diagram) 官方样例。

## 订单状态图

对应 `UML状态图.puml`，属于行为性图。六个业务状态为待确认、待付款、待交付、交付中、已完成、已取消。“交易进行中”只是包围前四种状态的复合状态，不新增数据库业务状态。
按用户的简化意见，主线竖排，取消只保留一条复合状态退出箭头，详细条件集中在图例；删除重复起点、长注释引线和图中的改约回环。此图展示主流程及取消规则概括，非穷举全部事件的实现状态机。

| 重点 | 本图表达 |
|---|---|
| 创建订单 | 成功预约、库存占用和快照建立后进入待确认；失败请求不创建订单 |
| 确认交易方式 | 卖家接受且双方确认同一方案后，线上售卖进入待付款，线下见面或赠送进入待交付 |
| 付款与代交 | 有效付款才能转为待交付；只有线上已付款或赠送能被代交人取件 |
| 完成条件 | 付费须已付款且已收货，赠送须已收货，代交还须已交件 |
| 系统取消 | 预约起满24小时卖家仍未接受，或进入待付款起满30分钟未付款，均可自动取消 |
| 普通取消 | 未付款售卖须双方同意；一方申请不释放库存，也不暂停原倒计时 |
| 赠送与异常 | 赠送取件前可取消；已付款售卖或赠送取件后由管理员核实异常，已取件须先核实退回 |
| 代交改约 | 简洁图不单独展开回环；需求仍保留失败后双方改约见面、停止旧任务并回到待交付 |
| 结束状态 | 已取消不恢复交付；已完成不退回待确认，售后记录独立处理 |

从复合状态到已取消的唯一取消箭头，概括各进行中状态满足阶段规则时的取消，不表示任何阶段都能无条件取消。24小时从预约成功起算，30分钟从进入待付款起算；自动超时无需双方同意，普通取消申请不暂停倒计时。
待确认同时包含“卖家尚未接受”和“已接受但方案尚未双方确认”两种情况；24小时超时只针对卖家尚未接受，不能在已接受后因方案未定而套用该超时。
线下订单的付款确认和收货确认可以先后发生，因此见面完成的触发标为“付款或收货确认”，两项条件齐备时才转换。
代交异常退回、退款与售后有各自记录和状态；图中不以退款代替订单取消，也不让退回或退款成功直接增加可售库存。
终止节点仅表示订单常规状态流结束，历史记录继续保存，资金对账或售后不因此停止。

## 交易时序图

对应 `UML时序图.puml`，属于交互性图。先选择“售卖商品、线上付款、见面交付”的正常成功场景，使用买家、卖家、平台后端、数据库和支付渠道五条生命线，控制图面复杂度。

1. 买家提交预约，平台在同一事务内检查当前商品与数量、占用库存、创建预约和订单快照，成功才返回订单。
2. 卖家接受，双方确认同一付款和交付方案后，平台保存方案并进入待付款。进入该状态时开始30分钟计时，本图不展开超时分支。
3. 买家完成渠道付款，平台核验渠道通知和有效订单状态，幂等记录成功付款，进入待交付；此时尚未向卖家结算。
4. 见面交付后，买家确认收到；平台核对付款与收货条件，完成订单并保存结算任务，才向卖家转交货款。

平台后端生命线是现有组件图中应用入口及其协调模块的概括，不代表删除模块划分。图中只保留关键数据库交互，身份核验、日志和其他普通保存不逐条展开。
`critical` 表达需要整体保护的预约事务；数据库实现仍须依靠事务、条件更新和唯一约束，图形本身不保证并发正确。
完成回复位于结算调用之前，明确订单完成不以结算成功为新增条件。本图只展开成功结算；失败时结算保持待处理并提醒管理员，后续按原幂等键重试，不重复转款。
重复预约返回已有记录；无效状态、库存不足等失败请求整体回滚。支付超时后的迟到成功仅退款，不得恢复订单。上述异常、线下付款、免费赠送、平台代交和售后退款可在后续审查中决定是否增加独立时序场景。
