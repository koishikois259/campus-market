# 状态图与时序图初稿说明

日期：2026-11-04；版本：订单状态图 v0.3，售后申请状态图初稿 v0.1，时序图 v0.4。

各图沿用实验一需求与现有类图、组件图。符号参考 [PlantUML 状态图](https://plantuml.com/zh/state-diagram) 和 [PlantUML 时序图](https://plantuml.com/zh/sequence-diagram) 官方样例。

## 订单状态图

对应 `UML状态图.puml`，属于行为性图。六个业务状态为待确认、待付款、待交付、交付中、已完成、已取消。“交易进行中”只是包围前四种状态的复合状态，不新增数据库业务状态。
按用户的简化意见，主线竖排，取消只保留一条复合状态退出箭头，详细条件集中在图例；删除重复起点、长注释引线和图中的改约回环。此图展示主流程及取消规则概括，非穷举全部事件的实现状态机。

| 重点 | 本图表达 |
|---|---|
| 创建订单 | 成功预约、库存占用和快照建立后进入待确认；失败请求不创建订单 |
| 确认交易方案 | 售卖或赠送在商品发布时确定并写入订单快照；卖家接受且双方确认同一方案后，售卖且线上付款进入待付款，售卖且线下付款或赠送进入待交付 |
| 付款与代交 | 有效付款才能转为待交付；只有线上已付款或赠送能被代交人取件 |
| 完成条件 | 付费须已付款且已收货，赠送须已收货，代交还须已交件 |
| 系统取消 | 预约起满24小时卖家仍未接受，或进入待付款起满30分钟未付款，均可自动取消 |
| 普通取消 | 未付款售卖须双方同意；一方申请不释放库存，也不暂停原倒计时 |
| 赠送与异常 | 赠送取件前可取消；已付款售卖或赠送取件后由管理员核实异常，已取件须先核实退回 |
| 代交改约 | 简洁图不单独展开回环；需求仍保留失败后双方改约见面、停止旧任务并回到待交付 |
| 结束状态 | 已取消不恢复交付；已完成不退回待确认，售后记录独立处理 |

从复合状态到已取消的唯一取消箭头，概括各进行中状态满足阶段规则时的取消，不表示任何阶段都能无条件取消。24小时从预约成功起算，30分钟从进入待付款起算；自动超时无需双方同意，普通取消申请不暂停倒计时。
待确认同时包含“卖家尚未接受”和“已接受但方案尚未双方确认”两种情况；24小时超时只针对卖家尚未接受，不能在已接受后因方案未定而套用该超时。
用户指出，售卖或赠送不应在待确认阶段重新选择。v0.3 将箭头改为“双方确认方案”和明确的分流条件：售卖协商付款与交付方式，赠送只协商交付方式。线下付款只能见面，不能选择代交。
线下订单的付款确认和收货确认可以先后发生；图中以“见面交付［完成条件满足］”概括，两项确认齐备时才转换。
代交异常退回、退款与售后有各自记录和状态；图中不以退款代替订单取消，也不让退回或退款成功直接增加可售库存。
终止节点仅表示订单常规状态流结束，历史记录继续保存，资金对账或售后不因此停止。

## 售后申请状态图

对应 `UML售后申请状态图.puml`，补充描述 AfterSaleRequest 的独立生命周期；原订单仍保持已完成。它与订单图同属状态图，不作为新的 UML 图种计数。

正常主线为“待卖方处理 → 待退货 → 待验收 → 退款处理中 → 已退款”。卖方拒绝进入“卖方已拒绝”，买方可申请管理员核查；提交申请满48小时卖方仍未答复时，买方也可申请介入，不自动进入核查或退款。管理员同意进入待退货，驳回则进入“申请被驳回”。

有效申请须符合订单原售后声明、买方身份、收货后168小时（含边界）及可退数量限制。正常状态含义与资金条件在报告中简述，图中不堆叠长注释。

验收通过后才进入退款处理中。线上已结算货款须先由卖方返还，资金未到位或退款失败仍保持处理中并记录原因、提醒管理员；线下由买方确认收到退款才记为成功。部分退货累计不能超过原数量和金额，退回或退款不直接恢复可售库存。

本图为简洁初稿，未逐条画出沟通、验收异常和重试回环，异常继续保留记录并交管理员核实，不能把验收未通过视为退款成功。卖方拒绝不是最终终止，历史答复保留；管理员核查结果和成功退款分别结束本次售后处理。

## 交易时序图

对应 `UML时序图.puml`，属于交互性图。选择“售卖商品、线上付款、见面交付”的正常成功场景，保留买家、卖家、平台后端、数据库和支付渠道五条生命线；v0.4 按用户意见恢复三个主要阶段。

1. 买家提交预约，平台在同一事务内检查当前商品与数量、占用库存、创建预约和订单快照，成功才返回订单。
2. 卖家接受，双方确认同一付款和交付方案后，平台保存方案并进入待付款，记录起算时间；30分钟从进入该状态起算。
3. 买家完成渠道付款，平台核验渠道通知和有效订单状态，幂等记录成功付款，进入待交付；此时尚未向卖家结算。
4. 见面交付后，买家确认收到；平台核对付款与收货条件，完成订单并保存结算任务，才向卖家转交货款。

当前图以“预约与方案确认—线上付款与交付—收货与结算”分段，保留21条消息和两行简短图例，移除付款 `opt`、`alt` 框。后两阶段展示付款有效后的正常路径，便于连续阅读。

异常规则在文字中保留：本次付款失败且未超时仍待付款、允许重试；进入待付款满30分钟仍未付款，由后端超时任务校验并取消，仅释放占用一次，不依赖买家是否点击付款。失败或取消不能继续交付和结算。付款通知与超时任务的冲突由数据库当前状态和原子条件更新处理。

平台后端生命线是现有组件图中应用入口及其协调模块的概括，不代表删除模块划分。图中只保留关键数据库交互，身份核验、日志和其他普通保存不逐条展开。
`critical` 表达需要整体保护的预约事务；数据库实现仍须依靠事务、条件更新和唯一约束，图形本身不保证并发正确。
完成回复位于结算调用之前，明确订单完成不以结算成功为新增条件。本图只展开成功结算；失败时结算保持待处理并提醒管理员，后续按原幂等键重试，不重复转款。
重复预约返回已有记录；无效状态、库存不足等失败请求整体回滚。支付超时后的迟到成功仅退款，不得恢复订单。上述异常、线下付款、免费赠送、平台代交和售后退款可在后续审查中决定是否增加独立时序场景。

v0.2 按用户意见将图底部三行长说明精简为两行，保留场景范围、预约失败回滚和重复请求无重复效果；原有21条消息保持不变。

### 分支表示

时序图可用 `alt / else` 将不同条件下的交互放在同一框的不同区段，某次情形按对应条件展开。例如有效付款成功、未超时的本次付款失败、满30分钟仍未付款。失败仍待付款，超时自动取消，后续交付与结算只接在有效付款成功路径中；不能把公共后续流程放在分支外让失败情形也进入交付。

`opt` 表示满足条件才执行的一段交互，`loop` 表示按条件重复；退款或结算重试仍须防止重复资金效果。交易方案不同也可用 `alt`，但售卖或赠送须依据订单原快照，不能临时改变商品交易类型。

v0.2 在私有工作目录生成局部分支示例；v0.3 按用户要求将付款成功、失败和超时加入正式图。用户随后认为分支版较乱，偏好初版的三阶段展示，v0.4 恢复正常主线，失败、超时、迟到付款及结算失败规则由文字说明补充。分支版保留在 Git 提交 `f6fd2b4` 中。
