# 组件图初稿说明

版本：AI 初稿 v0.1；日期：2026-11-02。

这是选定的第二种 UML 图，属于结构性图。它说明模块职责和依赖，与描述对象成员的类图互补。
使用 PlantUML 绘制，符号依据 [官方组件图样例](https://plantuml.com/zh/component-diagram)。

## 模块划分

| 模块 | 职责 | 主要关联类 |
|---|---|---|
| 应用入口 | 接收请求、调用权限检查、协调跨模块操作 | CampusMarket 对应的应用入口职责 |
| 身份与权限 | 邮箱注册登录、角色授权、资源归属检查 | User、Role |
| 商品与库存 | 草稿、审核、发布、修改、下架、组合查询和数量控制 | Product |
| 预约与订单 | 预约、卖家确认、方案确认、取消、收货与超时处理 | Reservation、Order |
| 支付与退款 | 支付结果、线下收款确认、收货后结算、返款和退款 | Payment 及两个子类 |
| 交付与售后 | 任务分配、取件交件、失败处理、售后申请、介入与验收 | DeliveryTask、AfterSaleRequest |
| 平台管理 | 举报与违规限制、日志查询、成交和赠送统计 | Report 及相关查询结果 |

用户界面包含普通用户、代交人、管理员的操作入口；这些不是三个互不相干的账号体系。邮箱和支付画在后端边界外，用命名依赖线标出接口调用；图中仅显式画出业务接口圆圈，避免重复节点。
业务数据库保存用户、授权、商品审核、预约订单、支付结算退款、交付售后、举报和日志等记录。图中的数据库文字仅为摘要，不限制实际存储范围。

## 主要交互

1. 界面调用后端提供的业务接口。应用入口核对身份、角色及资源范围，再协调相关模块；后台自动任务也通过受控业务入口处理。
2. 预约与订单依赖商品与库存完成数量占用、取消释放。预约、快照、订单和占用在同一数据库事务内提交，不能只更新其中一部分。
3. 线上资金操作通过通用支付接口接入渠道，初期使用模拟实现。线下付款只保存卖家确认，不调用线上付款；赠送不产生支付。
4. 售后批准并验收通过后才请求退款。支付与退款模块仍需校验原支付、可退金额及是否先完成卖家返款，不能仅凭一次界面点击退款。
5. 收货后结算、付款后允许交付、代交失败改约等跨模块业务，由应用入口协调。图只展示主要静态依赖，不用箭头冒充订单状态流或时序。
6. 每个模块通过其数据访问代码保存记录；共用数据库不表示可以任意改写其他模块的数据。失败操作也保留日志，查询按用户范围过滤。

## 符号与范围

- 带组件标识的矩形表示组件，圆形表示业务接口；接口与提供方之间用实线连接，调用方用虚线箭头指向接口。邮箱和支付接口以调用线名称概括。
- 虚线箭头从依赖方指向被依赖方。数据库图形表示持久化存储，业务模块分组到数据库的连线概括各模块的数据访问，避免逐条绘制重复线。应用入口到业务分组的依赖表示对其中各模块分派请求。
- 后端内的组件是 Java 应用中的职责模块，初稿按一个应用、一个数据库设计，不要求拆成独立微服务。
- 类图的一个类不必对应一个组件，一个组件通常包含多个实体、服务和数据访问实现。
