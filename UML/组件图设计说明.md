# 组件图设计说明

版本：v0.2，按用户审查意见调整；日期：2026-11-04。用户已确认本版，并要求纳入实验报告。

本图属于结构性图，以八个后端业务模块为主体，前端、数据库和外部服务置于主体之外。采用 PlantUML [官方组件图样例](https://plantuml.com/zh/component-diagram)中的组件、分组及依赖符号。

## 模块划分

| 模块 | 核心职责 | 对应主要类 |
|---|---|---|
| 用户 | 邮箱注册登录、账号信息、角色授权与账号限制 | User、Role |
| 商品 | 草稿、审核发布、查询、修改下架、售后声明与库存 | Product |
| 预约 | 按数量预约、卖家接受或拒绝、双方确认交易方案 | Reservation |
| 订单 | 成交快照、状态、取消协商、超时处理与确认收货 | Order |
| 支付 | 线上付款、线下收款确认、收货后结算与退款 | Payment 及其子类 |
| 代交 | 管理员分配任务、代交人取件交件、失败与改约 | DeliveryTask |
| 售后 | 申请与卖家处理、管理员介入、退货验收及退款进度 | AfterSaleRequest |
| 平台管理 | 举报处理、违规限制决策、日志查询与统计 | Report 及相关查询结果 |

用户模块提供身份和角色信息，各业务模块同时核对资源归属。管理员的商品审核、代交分配和售后介入分别由对应模块完成，平台管理不包揽所有管理员操作。

## 图中主要依赖

1. **预约 → 商品、订单**：检查并占用库存，同时建立预约、订单及快照。预约成功时即建立订单，后续接受预约不会再创建第二笔订单；交易方案确认结果由订单保存。
2. **订单 → 支付**：核对付款结果，并在买方收货、满足完成条件后发起线上结算。付款成功不能提前向卖家结算。
3. **代交 → 订单**：检查交易方案和交付资格，取件、交件时同步订单进度。代交交件仍需买家确认收货；失败改约须双方确认并停止旧任务。
4. **售后 → 订单、支付**：核对原订单、声明、期限和可退数量；售后批准且退货验收通过后申请退款，支付模块再检查资金和可退金额。
5. **平台管理 → 用户、商品**：管理员决定违规限制后，分别调用账号限制或商品限制功能；已有订单与资金记录保留。

上述箭头表示模块依赖，不表示业务执行的时间顺序，也不要求一次操作只调用一个模块。取消后释放占用、支付通知更新订单、统计读取交易结果等协作在图中省略，具体规则仍按需求执行。

## 外围支撑

- **前端界面**：提供买卖、代交和管理入口，通过后端业务接口提交请求与展示结果；权限和业务规则由后端实际校验。
- **业务数据库**：持久化用户、商品、审核、预约订单、资金、交付售后、举报和日志。后端边界到数据库的连线概括各模块的数据访问，不是让业务分组本身执行数据库操作。
- **邮箱服务**：供用户模块发送验证码。
- **支付渠道**：供支付模块处理线上付款、结算和退款，初期使用模拟实现；线下只记录确认，赠送不调用支付。

## 划分理由与实现约束

预约侧重交易前的申请与协商，订单负责交易记录及生命周期；代交负责交付执行，售后负责收货后的退货争议，分别拆分可明确职责。商品与库存仍在同一模块，支付、结算和退款集中管理资金记录。

这些模块属于同一个 Java 应用，可对应不同代码包。跨模块业务由应用层协调，技术入口与协调代码在此图中概括，不单独占据主体位置。预约、订单快照和库存占用须在同一事务中提交；有效取消与释放占用也须保持一致，重复请求不得产生重复效果。

各模块通过自己的数据访问代码使用同一数据库，数据修改应由所属模块提供的业务方法完成。平台管理提供日志查询，其他模块仍须记录关键操作和失败结果。公共权限、日志和完整依赖未逐条连线，以保持图面清晰；简化展示不删减需求。
