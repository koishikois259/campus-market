## 核心类与职责

| 类 | Java 命名 | 主要职责 |
|---|---|---|
| 用户 | User | 登录、角色及权限检查 |
| 商品 | Product | 商品基本内容、审核发布与下架 |
| 预约 | Reservation | 购买数量、卖家接受/拒绝、确认期限 |
| 订单 | Order | 成交快照、方案确认、取消与收货 |
| 支付记录 | Payment | 付款金额、付款状态的共同抽象 |
| 线上支付 | OnlinePayment | 支付渠道结果、收货后结算与原路退款 |
| 线下付款 | OfflinePayment | 卖方确认收款 |
| 代交任务 | DeliveryTask | 被分配代交人的取件、交件与失败记录 |
| 售后申请 | AfterSaleRequest | 退货数量、退款金额、申请处理与验收 |
| 举报 | Report | 记录被举报商品或订单及处理结果 |

角色集合可含买家、卖家、代交人、管理员，同一账号可以兼任，因而不把四种角色画成互斥的用户子类。
线上支付与线下付款继承抽象的支付记录，共同属性放在父类，各自保留差异成员。

## 关系如何阅读

- 一个用户可以发布多件商品、发起多次预约和提交多条举报；一件商品可以被多次预约。
- 一次成功预约对应一笔订单，预约与订单同时创建。
- 一个订单可以有多条支付尝试、代交任务历史或部分退货申请。`0..*` 表示历史记录数量，不代表可以重复有效付款或同时存在多条有效代交路径。
- `1` 表示一个，`0..*` 表示零个或多个；空心三角指向父类。
- 举报目标通过“目标类型 + 目标编号”引用一个商品或一个订单，图中省略两条目标线以减少交叉。
- 用户与订单参与人、管理员审核人等关系通过实际记录的编号确定，本张图只画核心连线，未画出不等于取消这些关系。

## 精简时仍须保留的需求约束

此图是核心设计视图，不是完整数据库结构；未展示的记录和字段仍须在后续实现中补足，不能据此删减实验一需求。

- 商品状态与可用数量分开；编辑、审核、下架均先检查角色、资源归属及有效预约/订单，不能任意跳过审核。
- 订单成交单价、数量和售后声明是历史快照，不受商品后续修改影响；实际实现还要保存商品名称等快照字段。
- 预约占用库存和订单创建保持事务一致；重复请求、重复释放、重复资金通知只产生一次业务效果。
- 未付款售卖订单普通取消须双方同意；已付款不得普通取消。卖家拒绝待处理预约和 24 小时、30 分钟超时仍按原需求处理。
- 交易方式须双方确认；线下付款只能见面交付，赠送不产生付款或退款。
- 线上支付成功后先等待收货再结算；线下付款只由卖家确认。只有满足付款和收货等条件，付费订单才能完成。
- 平台代交只能由被分配的有权限人员处理；未付款线上订单不能取件，交件不等于收货。
- 售后按原订单声明，在收货起 168 小时内申请；卖家应在 48 小时内答复，拒绝或超时可申请管理员介入；验收后才退款。
- 退款失败保持处理中；已结算货款先由卖家返款。退回商品需重新审核，不因退款成功直接恢复可售。
- 模拟与真实支付、退款记录、结算记录、审核历史、关键日志和统计仍按需求独立保留；本图为避免过密不逐一画成类。

方法签名表达设计职责，未展开操作者参数、校验和服务调用。Java 实现时，实体操作、授权检查、数据库访问及外部渠道调用仍应分层；不在用户类里集中实现交易逻辑，不在订单类里直接调用支付 SDK。
