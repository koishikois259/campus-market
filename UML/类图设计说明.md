## 建模约定

- 类名同时给出中文语义和英文实现名；属性、操作使用中文说明语义，类型采用 Java 风格。这是设计级 UML，不是直接生成的 Java 源码。
- `-` 表示私有属性，`+` 表示公开操作。参数为设计级简写，具体 DTO 和参数类型留待实现细化，不表示可直接编译。
- 编号使用 `UUID`，金额使用 `BigDecimal`，时间点使用 `Instant`、时长使用 `Duration`。`[0..1]` 表示可选值，`{readOnly}` 表示构造后不再改写。
- 数量使用整数。标记 `/` 的净统计值为推导属性，不是额外维护的一份余额。
- 类图中的关联表达业务关系，不要求 Java 中全部保存双向对象引用。跨聚合、跨模块优先保存编号，通过服务和仓储查询，减少对象互相牵连。
- 黑菱形只用于明确组成部分：订单拥有快照，商品拥有图片和库存。历史审核、订单和资金记录不随商品下架或账号限制级联删除。
- 版本号配合数据库条件更新；幂等键配合唯一约束。仅画出这些字段不能证明系统已具备并发正确性，还须在后续实现及测试中验证。

## 为什么这样划分类和继承

### 用户采用角色关联

`User — RoleGrant — Role` 表达账号拥有的多种角色。同一用户可以同时是买家、卖家，也可以另获代交权限。
不建立 `Buyer extends User`、`Seller extends User` 的互斥账号体系。管理员和代交权限必须经授权入口授予，不能相信注册请求中的角色字段。
角色权限之外，还须校验资源所有者、订单参与人和任务分配对象；拥有代交角色不代表可处理全部任务。

### 仅在具备共同语义时继承

1. `PaymentRecord` 是抽象父类，共享订单编号、金额、状态和确认时间。`OnlinePayment` 处理渠道结果，`OfflinePayment` 保留卖家确认事实。渠道回调和线下确认不混成一个布尔字段。
2. `Restriction` 是抽象父类，共享限制原因、管理员、期限和解除记录。`AccountRestriction` 指定用户与受限权限，`ProductRestriction` 指定商品与处置方式。
3. `MockPaymentGateway` 实现 `PaymentGateway` 接口，用于后续模拟测试。接口实现与类继承使用不同 UML 箭头。

售卖与赠送目前共享大部分商品和订单生命周期，用 `TradeType` 区分，不为增加继承层数而拆分子类。初稿不引入没有独立业务价值的统一实体父类。

### 高内聚与低耦合的落实位置

- 用户域处理身份及授权；商品域处理内容、审核和数量；交易域处理预约、协商和订单生命周期；资金域处理支付、结算、返款和退款；履约域处理交付与售后；治理域处理举报、限制、日志及统计读取。
- 实体维护自身状态与局部约束，应用服务协调多个实体。实体不直接调用外部支付、邮箱或数据库，也不读取其他模块的内部表结构。
- 仓储按业务职责分组，后续实现可细分为具体聚合的 Repository，不做一个包含所有业务操作的共享数据库类。
- 业务服务依赖支付接口，模拟与真实渠道在适配层替换；不在 `Order` 内写具体微信或支付宝调用。
- 订单服务可以读取支付与履约事实，不依赖具体渠道适配器；应用服务之间不建立互相调用的环。
- 这些是初稿采用的边界，不代表“零耦合”。库存与预约、付款与交付、售后与退款存在需求要求的业务联系，必须保留。

## 关键业务约束

### 预约、库存与订单

成功的预约对应一笔订单，二者同一事务创建；商品快照同时固化。失败不留下孤立订单，也不能只扣库存不创建记录。
重复请求以“买家编号 + 请求幂等键”返回原结果。预约占用数量与可售数量原子变更，旧页面还要核对商品内容版本、发布状态及当前价格。
有效预约或进行中订单存在时，卖家不得修改或下架；管理员违规限制另走治理流程，不删除既有订单。

`Inventory` 的可售数量和预约占用数量为当前计数，累计发出数量为历史计数，不能直接把三者相加当作永久不变的总库存。
每条预约保存 `HoldStatus`：占用中、已释放、已发出。释放动作与其状态更新同一事务生效，保证只释放一次；取件或见面交付的数量由占用转为已发出。
退回数量通过独立批次跟踪，只有完好且复审通过后才能重新进入可售，防止退款或重复验收直接加库存。

### 方案与取消

同一订单保留多版交易方案，但最多一个当前有效方案；买卖双方必须确认同一版。原订单快照不因改约而改变。
线上售卖可见面或代交；线下付款只可见面；赠送没有付款步骤。
普通未付款售卖取消须双方同意，实际执行前再核对付款状态；申请不暂停超时倒计时。
卖家拒绝只限未接受预约；24 小时卖家未确认、30 分钟线上未付款为自动取消例外。
赠送取件前可取消，取件后由管理员核实异常；已付款不能用普通取消入口处理。

### 支付、结算和退款

订单可以有失败支付尝试，但最多一笔有效业务付款。真实渠道若发生额外实收或迟到成功，必须保留该资金事实并退款，不能仅用“重复请求”丢弃。
线上支付是资金已付，不是卖家已收结算；买家确认收货并满足完成条件后才结算。线下付款只记录该订单卖家确认。
渠道通知要验签或查询核实；`MOCK` 与 `LIVE` 明确分开，模拟成功不代表真实扣款。
退款关联原订单和原支付，方式与支付子类匹配。售后来源、异常取消来源、迟到付款来源三选一：

- `AFTER_SALE`：来源编号指向售后申请；批准并验收通过后执行。
- `EXCEPTION_CANCEL`：来源编号指向交易异常处理记录；管理员核实后执行。
- `LATE_PAYMENT`：以原线上支付编号为来源事实；订单维持已取消，不恢复交付。

普通未付款取消与赠送不生成退款。原货款已结算时，记录卖方返款到账后才退款；否则持续处理中，不假定平台垫付。
失败保存最近原因、提醒管理员，成功确认后才进入成功状态。一次业务退款使用同一幂等键重试，不为每次失败新建一笔有效退款。
线上部分退款累计不得超过原实收，售后数量同时不得超过原订单有效可退数量。
线下售后由买家确认收到退款，不调用平台线上退款接口。

### 售后与交付

代交任务只指派给有权限人员，同一订单最多一条有效代交路径，任务历史可多条。线上未付款不能取件，未取件不能交件，交件不能替代买家收货。
无人可分配时保留订单和交易方案，不必先创建一个没有代交人的任务；共同改约后停止旧任务。
售后根据原快照声明校验资格，提交时间允许等于收货时间加 168 小时，晚于该时刻才拒绝。
同一订单的成功退货数量和其他有效申请占用一起锁定检查，防止多次申请超退。
48 小时未答复只是提醒与介入资格，不自动同意、退款或完成验收。
正常售后批准后仍须退回验收；管理员介入记录与双方证据关联到同一售后，保留核查依据。

### 日志、限制与统计

举报的类型与编号只指向一个商品或一个订单，入库校验目标存在；不是同时关联两个目标。
账号/商品限制不覆盖原有付款、订单和退款历史。设置与解除必须记录管理员及原因。
系统任务用 `ActorType.SYSTEM` 与任务代码标识，人工操作用 `USER` 与用户编号标识。
关键失败和拒绝日志也必须可靠保存，不能随着失败业务事务回滚而消失；日志至少保留 180 天，本期不提供导出。
统计只读取已完成订单与成功售后退款，不把申请中或失败退款提前扣减；赠送另计。迟到支付退款不属于已完成订单的售后净额扣减。

## 需要用户审查的设计选择

以下是 AI 初稿提出的实现选择，不是已经完成的人工判断：

1. 是否接受按六个领域分包，并将交付与售后放在同一领域？后续规模增大可再拆分。
2. 是否认可“预约成功即同一事务创建订单”，以保证一对一和历史快照一致？
3. 初稿用多版交易方案保留双方协商和改约历史，是否符合你预期的 UI 操作？
4. 初稿以单次申请一次最终验收为简化：申请可以针对原订单的一部分数量，但本次申请的数量需整体通过；不符时进入异常核查。若需同一次申请内分批验收或部分接收，应调整验收关系与退款数量分配。
5. 本稿依据需求把账号限制到期后的解除保留为管理员操作；具体到期处理策略需人工核对，不能仅凭此图新增自动解除规则。
6. 商品名称和描述字数上限、真实支付费率、实际渠道适配、索引细节仍未确定，初稿不虚构数值或已通过的测试。
