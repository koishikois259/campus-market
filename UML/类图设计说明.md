## 本次精简的表达方式

参照 [PlantUML 官方类图文档](https://plantuml.com/zh/class-diagram) 的类间关系、关系标签和聚合成员可见性样例，保留 11 个主要类，减少类框中的重复引用和次要方法。核心业务结构沿用 v0.3。

| 图中标记 | 本图中的含义 |
|---|---|
| `o-->` | 共享聚合及导航方向，空心菱形在持有集合的一端；本图用于平台用户、用户商品/买方预约、订单支付记录这些独立保留的对象集合 |
| `-->` | 可导航关联，例如商品保存预约引用，预约保存订单引用 |
| `<|--` | 继承，空心三角指向支付记录父类 |
| `-成员名` | 私有关联端角色名，与成员字段表达相同的属性，不在类框重复列出 |
| `1`、`0..*`、`0..1` | 恰好一个、零到多个、可选一个；多值关联可用 List 或 Map 实现 |
| `/卖方预约` | 推导成员，通过用户发布的商品和预约买家关系查询，不另维护一份记录 |

对象作为成员不必使用菱形；普通引用使用关联即可。共享聚合表达整体与独立对象集合，本图没有严格依附整体生命周期的独占部分，未使用黑心菱形组合。
例如 `User "1" o--> "0..*" Product : -发布商品` 表示用户持有发布商品集合；`Reservation "1" --> "1" Order : -对应订单` 表示预约持有一个订单引用。连线也能表达成员，因此无需重复写 `发布商品: List<Product>` 和 `对应订单: Order`。

## 保留的结构

共 11 个主要类：交易平台、用户、商品、预约、订单、抽象支付记录、线上支付、线下付款、代交任务、售后申请、举报。

| 调整 | 表达方式 |
|---|---|
| 平台统一管理记录 | CampusMarket 使用 Map 按 UUID 管理用户、商品、预约与订单 |
| 用户的业务关联 | 发布商品、买方预约、卖方预约、代交任务使用 List 表达 |
| 多角色权限 | User 的 Set<Role> 包含 BUYER、SELLER、COURIER、ADMIN，可按授权增减 |
| 商品的业务记录 | 关联发布者，保存预约和举报集合 |
| 预约的参与人 | 关联买家、商品与订单，卖家通过商品发布者确定 |
| 订单的关联 | 明确买卖双方、商品、付款及交付方式、售后和举报集合 |
| 交易历史快照 | 使用只读值对象 OrderSnapshot 保存商品名、单价、数量、总额、交易类型和售后声明 |
| 代交与用户 | 任务明确原订单、被分配代交人和分配管理员 |
| 售后与用户 | 明确原订单、申请买家、可选介入管理员，卖家由订单确定 |
| 举报对象 | 保留举报人、可选处理管理员，商品目标与订单目标恰有一个非空 |

用户的售后与举报入口采用查询方法，不再为每个查询结果额外增加常驻集合。不同对象的关联集合引用同一条业务记录；Java 实现不应分别复制并维护其状态。
Map 是原型的内存索引设计，不能代替 REQ-024 要求的持久化。后续需保存到数据库或可靠存储，重启后重建索引并验证已成功订单仍完整可查。
图中省略各实体共同拥有的 UUID 字段、部分参与人、处理时间与次要操作。原有角色授权、管理员介入、失败处理等职责保持不变。平台仅画用户集合，商品/预约/订单 Map 索引仍按结构方案实现。
代交任务与用户的连线表示该用户执行的任务；分配管理员单独列为成员。举报人、申请买家等保留在类框，避免再增加交叉线。关联线表达业务关系，实际实现可按边界使用对象引用或编号引用，不要求全部建立双向对象图。

## 仍须遵守的约束

1. 售后声明使用 AfterSalePolicy：UNDECLARED、SUPPORTED、NOT_SUPPORTED。售卖商品未声明不能发布；赠送金额为零且无支付流程。
2. 商品状态与可用数量分开。有效预约或进行中订单存在时，卖家不得修改或下架；管理员违规处置走受限入口。
3. 预约、库存占用与订单创建同一事务完成。成功预约对应一笔订单；重复请求只返回原结果，取消只释放一次占用。
4. 用户的可售商品是筛选结果；售罄或下架商品保留历史。退回验收或退款成功不直接恢复库存，须按原需求重新审核。
5. 成交快照构造后不可改写。付款与交付方案须双方确认同一结果；线下付款只能见面，赠送无需付款。
6. 未付款售卖普通取消须双方同意；已付款禁止普通取消。卖家拒绝待处理预约、24 小时卖家未确认及 30 分钟线上未付款仍按原需求处理。
7. 支付尝试、代交任务及售后申请可有历史多条，不表示允许重复有效付款、并行有效代交或超量退货。
8. 线上收款、结算与退款仍是不同资金事实。买家收货后才结算；已结算退款先确认卖家返款到账；模拟与真实环境分开。
9. 代交操作须核对任务分配；线上售卖未付款不能取件；代交交件不能代替买家确认收货。
10. 售后提交不晚于收货后 168 小时；卖家 48 小时内答复。拒绝或超时后由买家申请管理员介入，批准后仍需验收退货再退款。
11. 商品举报与订单举报互斥。管理员审核、分配、处理举报和介入售后均须校验角色；普通用户还需校验资源归属。
12. 审核历史、退款、结算、沟通证据、关键日志与统计等细节沿用需求，不因简洁类图省略类框而删除。

Role、各 Status、PaymentMethod、DeliveryMethod 等为枚举。OrderSnapshot 是不可变值类型，包含商品名、单价、数量、总额、交易类型和售后声明。TradeAgreement 表达付款/交付方式及双方确认结果。为突出核心，两者均不展开为额外类框。
方法省略部分参数，Java 实现时应补全操作者与结果类型，并由应用入口协调授权、事务和外部渠道调用。UML 标记说明的是设计关系，不是 Java 容器的固定实现语法。
