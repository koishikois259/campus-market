# 实验二 AI 辅助设计使用记录

此文件记录真实协作过程，供后续报告引用与人工补充。AI 编写的初稿和修改不标注为人工完成。

## 2026-11-02：需求解读、图种选择与工具准备

- 使用场景：理解实验二要求，选择适合校园二手交易系统的四种 UML 图，比较 Java 与 C++，准备 PlantUML 工具。
- 生成结果：建议类图、组件图、状态图、时序图；建议 Java；下载 IntelliJ IDEA 的 plantuml4idea 官方插件安装包。
- 用户明确决定：提供今年新版要求，纠正旧附件中的报告 AI 使用限制和截止日期；决定使用 Java、从类图开始；随后反馈插件已安装。
- AI 输出的局限：最初按旧附件解释“报告禁止 AI 辅助”，新版实际允许；因此以用户后来提供的 2026 年要求为准。工具下载经历超时，最后从官方 CDN 分段获取并检查 ZIP 完整性。
- 修改优化结果：采用新版要求、Java 和本地 PlantUML；工作分支为 `UML-and-UI`。
- 人工体验与优缺点评价：待用户补充，不由 AI 冒充。

## 2026-11-02：UML 类图 AI 初稿 v0.1

- 使用场景：用户要求根据实验一需求生成类图初稿，明确类的划分、继承、实体属性，并考虑低耦合与高内聚。
- 输入：`requirements.md` 的 REQ-001—REQ-028，以及用户关于 Java 和建模质量的要求。
- 生成结果：`UML/` 中的总览类图、六张领域属性详图、一张服务接口详图、复用模型片段及 `类图设计说明.md`。
- AI 提出的设计：角色关联代替买卖身份继承；线上/线下支付继承共同抽象父类；账号/商品限制继承共同抽象父类；跨域保存 UUID，通过服务与仓储协调。
- AI 自检与调整：将初稿编写过程中的通用持久化接口细化为按业务划分的仓储，保留独立事务边界；核对快照、取消例外、资金结算、售后验收、退回重审和幂等约束；执行 PlantUML 语法检查、渲染和图片布局检查。
- 优点分析（AI 自评，供人工核对）：实体按业务职责组织，关键关系与属性可追溯到需求；源文件复用，便于 Git 对比；避免用单一状态混淆订单、付款和退款。
- 局限分析（AI 自评，供人工核对）：完整需求带来较多实体；总览隐藏成员，需结合属性详图阅读；部分仓储和服务签名仍为设计级概览；一次申请一次最终验收等初稿选择需用户确认；图不能证明真实并发、权限或支付实现正确。
- 用户检查意见：尚未收到，待用户审查后如实追加。
- 人工修改或人工意见驱动的优化结果：尚未发生，不能把本次 AI 自检记作人工修改。
- 版本追踪：本次提交作为 AI 初稿基线；后续用户审查意见和修改应形成独立提交。

## 后续工作流讨论素材（待人工评价）

候选流程：人工明确范围与约束 → AI 生成可追溯初稿 → 自动检查语法与渲染 → 人工逐项核对需求与设计取舍 → AI 按明确意见修改 → Git 保留差异 → 人工验收。
这只是待评价的工作流，不是用户的个人体验结论。是否能把人的工作缩减到检查校对，需要结合后续实际审查中发现的问题、决策和修改量来判断。

## 2026-11-02：根据用户审查和参考样例精简类图 v0.2

- 使用场景：用户认为 v0.1 类图过于详细，希望参考 `实验2_221220064_刘姝俐.zip` 中的 UML 图，更简洁直观地展示关系、核心成员和方法。
- 人工审查意见（用户原话）：“你的类图太详细了，我要更直观的，按照zip里uml图的风格，更简洁，更直观的显示类之间的关系，类的核心成员及方法”。
- 参考分析：读取压缩包内的类图图片和 PlantUML 源文件；参考图为 6 个类的单张灰白类图，成员少、关系线直接、不分领域包。
- 生成结果：AI 将 34 个领域类及多张详图精简为 10 个核心类的一张类图，直接显示主要属性与方法；保留线上/线下支付继承关系和用户多角色设计。
- 修改优化：移除当前目录中的旧详图和模型片段；旧版保留于 Git 提交 `2eaf123`。新版源文件独立可渲染，输出 PNG、SVG，重写精简版说明。
- 优点分析（AI 自评）：减少技术细节和分散视图，核心交易关系可在单张图中阅读，更接近用户给出的样例。
- 局限分析（AI 自评）：不能据此直接生成完整数据库或覆盖所有异常处理；省略的快照、审核、结算退款记录、日志与统计仍须依据需求实现，设计说明明确了这些边界。
- 归属说明：用户作出设计方向判断，AI 完成具体修改和渲染；不是用户亲自编辑源码。本次属于人工意见驱动的 AI 修改。
- 用户对修改结果的后续评价：待用户检查，不预先填写已通过。

## 2026-11-02 类成员与关联的逐项讨论

| 使用场景和人工输入 | AI 讨论结果及取舍 | 采用或调整结果 |
|---|---|---|
| 用户提出用集合保存发布商品，以及作为买卖双方参与的预约 | 建议 List 表达关联，区分买方与卖方入口；在售商品按状态与数量筛选 | 用户类加入发布商品、买方预约和卖方预约，保留商品历史 |
| 用户提出举报应成为商品或订单的成员 | 同一举报只针对一个目标，多个集合引用同一记录 | 商品和订单加入举报集合，举报目标使用互斥约束 |
| 用户提出代交任务关联用户，并讨论普通用户、管理员、代交人的继承 | 固定继承不便增减代交权限，建议以角色集合表达授权 | 用户采纳角色方案；任务关联代交人及分配管理员，平台 Map 统一索引用户 |
| 用户追问权限是否作为用户成员 | 角色决定许可，实际操作还要核对资源归属 | 保留 Set<Role> 与权限检查方法 |
| 用户提出售后申请也应关联其他类 | 售后关联原订单、申请买家和介入管理员；卖家从订单确定 | 补全参与人，通过查询提供用户的售后入口 |
| 用户要求总结并提出类似改进，再统一修改 | AI 提出平台容器、售后声明三态、订单交易方式及收货时间、操作人参数 | 用户在后续消息明确采用，整合为 v0.3 |

优点分析：AI 能把口头意见转换为成员、关系及约束，并指出多角色和历史数据方面的取舍。局限分析：逐项增加集合可能再次造成图面拥挤，仍需人工决定哪些成员和连线应直接展示。以上讨论没有声称用户亲自编辑源文件。

## 2026-11-02 整合类图并同步编写报告 v0.3

- 使用场景：用户明确采用结构调整，要求生成新图和 Word 报告，先写类图部分；参考两个 ZIP 的报告，语言简洁，并体现个人审查与改进思路。
- 参考资料：实验一需求、当前类图、两份参考报告的类图说明与 AI 辅助章节；旧 `2.md` 的冲突要求按用户提供的 2026 年新版替换。
- 生成结果：11 个主要类的 PlantUML、PNG、SVG；两页 Word 阶段稿及可编辑 Markdown 源稿、生成脚本。
- 修改优化：平台集中索引记录；用户增加业务集合；举报明确唯一目标；代交及售后明确用户身份；补充成交快照、交易方式、收货时间及售后声明三态。报告用一张职责表和三段关系说明概括设计，另用两段记录 AI 初稿及人工审查驱动的改进。
- 优点分析：同一张图直接展示集合成员和业务参与者；报告与当前图片同步生成，便于继续增补。
- 局限分析：简洁图未展开全部历史、证据和资金记录；集合及权限字段仍需后续实现验证。AI 可以辅助写作和生成语法，不能代替需求和业务规则判断。
- 过程归属：用户提出并采纳方向，AI 编写源文件、辅助整理报告、渲染和检查排版；报告第一人称内容仅依据本次真实讨论。
- 验证：PlantUML 语法检查和 PNG/SVG 导出通过；Word 由本机 Microsoft Word 导出临时 PDF，再使用文档技能渲染页面进行视觉检查。常规渲染器因未安装 LibreOffice 无法直接转换，使用本机 Word 作为转换后端，没有安装额外软件。
- 后续方向：按“人工明确需求—AI 初稿—自动检查—人工审查—AI 修改—Git 留痕”推进其他图与 UI，不预先声称整个实验完成。

## 2026-11-02 简化展示并校对官方关系标记 v0.4

- 使用场景：用户认为整合图仍复杂，要求突出重点，并参照 PlantUML 官网在线上标明其他类对象作为成员。
- 参考资料：PlantUML 官方类图文档 https://plantuml.com/zh/class-diagram 的类间关系、关系标签、聚合成员可见性样例。
- 生成结果：保留 11 个核心类，将重复的集合与引用字段转移到带私有角色名和多重性的连线上；类框保留关键业务属性和方法；同步更新报告图片与符号说明。
- 优缺点分析：图面更紧凑，成员与关系无需重复阅读；省略了部分操作参数和辅助字段，具体实现仍须依据需求与结构说明补全。
- 修改优化：以空心菱形表示共享聚合、实线箭头表示可导航关联、空心三角表示继承；普通对象引用不一律标为组合。卖方预约改为推导成员，减少重复维护。
- 人工思考与执行归属：用户再次判断图面复杂并提出参照规范的方向，AI 查阅官网、执行改图及同步排版；未将 AI 自动调整冒充用户手工编辑。

## 2026-11-02 调整为 A4 纵向报告版式 v0.5

- 使用场景：用户要求图在报告中更完整、美观，希望适度放大或采用竖构图，避免改变报告页面大小。
- 生成结果：实体、属性及关系保持不变，仅调整排布方向、类间距和图例换行；Word 所有页面统一为 A4 纵向，类图等比例放入独立图页。
- 优缺点分析：纵向布局更适合常规报告，避免 A3 图页和文字拉伸；类图信息量仍较大，单独图页和适度缩小图页边距用于保证可读性。
- 修改优化：重新生成 PNG、SVG 与报告，检查同页图注、页尺寸和嵌入图一致性，并逐页检查 Word 实际渲染。
- 归属说明：用户提出排版目标，AI 完成布局和文档修改，不计作新的业务设计决策。

## 2026-11-02 组件图 AI 初稿 v0.1

- 使用场景：用户要求开始绘制下一个 UML 图，先形成初稿；按既定选择继续组件图。
- 输入与参考：实验一需求、已讨论的类结构、PlantUML 官网组件图样例。
- 生成结果：组件图 PlantUML、PNG、SVG 及独立说明，展示界面、应用入口、六个业务模块、邮箱/支付接口和业务数据库。
- 优点分析：以职责模块表达系统整体结构，保留预约与库存、售后与退款等关键协作，外部服务通过接口隔离。
- 局限分析：为保持简洁未画出全部数据访问和跨模块依赖，仍需用户审查模块边界；依赖图不能替代后续状态图和时序图。
- AI 自检优化：依照官网使用组件、接口、依赖箭头及数据库符号；避免把模块画成微服务部署，或把静态箭头解释为业务时间顺序。
- 人工审查与修改：尚未发生，待用户反馈后独立记录；本次作为组件图 AI 初稿基线提交。
